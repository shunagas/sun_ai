### 2026-09-06 ダッシュボードDB同期の恒久対応調査（問題1: 記録・現状維持／問題2: GitHub Actions導入は見送り）
9/5対応（41af54d）で追加した「note/YouTube夜間ルーティン・KPI日次更新ルーティンからダッシュボードDBへ書き込む」ステップが、実際には一度も機能していなかったことが判明。本人からの依頼を受けて調査・方針決定。

#### 問題1: Artifactへのwrite_dbが無人実行(クラウドルーティン)で毎回「承認待ち」のまま止まる
- **事実関係**：3つの日次クラウドルーティン（trig_016BTxynrNLntkH9HP4ry3ij=YouTubeチーム会議、trig_01Cnv16qFhBLUU73RPJ9Nmfh=noteチーム会議、trig_01Donjh5joe5NGJZtcHWiVVz=KPI日次更新）はいずれも記事/動画アイデアの追記・git commit/pushまでは正常完了しているが、追加したDB同期ステップ（Artifactツール`action:"write_db"`で`collection:"meeting"`/`collection:"kpi"`へ書き込む処理）で
  ```
  permission prompt Artifact: Claude wants to edit this artifact's data. Approving covers data edits to any artifact for the rest of this session.
  ```
  という承認プロンプトが出た時点で停止し、以降何も実行されずセッションが`requires_action`のまま終わっている。noteチーム（session cse_01M4RPf4K9PpU1952ZGAHLRJ, 2026-09-05T16:05 UTC発火）・YouTubeチーム（session cse_01X6DAa79r29rdWQaWPt4Xv9, 同16:09 UTC発火）とも同一箇所で停止しており、過去分も同様の可能性が高い。無人実行のクラウドセッションのため誰も承認できず、リポジトリ内のコードやルーティンのプロンプト文面をどう変えても直せない、**Anthropicプラットフォーム側の不具合**と判断。Claude Code公式ドキュメントの「ルーティンは権限モードの選択も承認プロンプトもなく完全自動実行される」という説明と矛盾する挙動であり、この点は既にAnthropicへフィードバック送付済み。
- **実害の範囲**：DB同期ステップはgit commit/pushとは独立した処理として設計済みのため、失敗してもgit側のやり直しは不要＝記事/動画アイデアの記録自体への実害はない。実害は「ダッシュボードの『本日の議事録』パネル・KPIスナップショットが更新されないまま古い日付で止まる」に限定される。
- **決定：DB同期ステップは無効化せず現状維持（コードは変更しない）**。理由：(1) 無効化してもgit側の信頼性が上がるわけではなく得るものがない一方、Anthropic側の不具合が解消された時に再度実装し直す手間が発生する。(2) この承認プロンプトは「無人のクラウドルーティン実行」でのみ問題になるものであり、本人が対話セッションでルーティンを手動実行した場合は承認可能なため、その経路では現状のコードのまま機能する。(3) 実害が「ダッシュボード表示が古いまま」に留まり、実データ（git上の記事/動画アイデア）を損なわないため、無効化する緊急性がない。
- **今後の運用**：Anthropicからのフィードバック回答・プラットフォーム側の修正を待つ。当面、ダッシュボードの議事録/KPIパネルが更新されていない場合は本人が手動実行 or 手動バックフィルで対応する（9/5対応時と同様）。開発部としてはこの問題を「対応不可（プラットフォーム側）」として追跡のみ行う。

#### 問題2: KPI日次更新ルーティンがnote.com/www.youtube.comへの通信をegressポリシーでブロックされ続けている（3日連続・9/3,9/4,9/5）
- **事実関係**：trig_01Donjh5joe5NGJZtcHWiVVzの直近3回（session cse_01WGuExwoiAvBRkpTLATp2jb, cse_01YViopnjiGchkcPxDgbhSGR, cse_01SqbVceofc9Jo5Sq19rZ9kW）はいずれもcurl・WebFetch双方でnote.com/www.youtube.comへの接続が`EGRESS_BLOCKED / connect_rejected (the egress proxy denied the CONNECT (organization policy))`で拒否され、安全策（全項目取得失敗時は書き込みしない）に従って何も更新せず終了。ルーティン実行環境（CCRサンドボックス）のegressはnpm/pypi/crates.io/GitHub関連などのアローリストのみで、note.com・www.youtube.comは対象外。RemoteTrigger作成/更新APIにもegressアローリストを変更するフィールドは確認できず、設計時点から一度もこのルーティンは正常機能していない。
- **検討した代替案**：GitHub Actionsのcronワークフローを本リポジトリに追加し、通常のインターネットアクセスがあるActionsランナー側でnote.com/YouTubeの公開データを取得してリポジトリ内ファイル（JSON等）にコミット、CCRルーティン側はそのファイルを読むだけにする構成。
- **決定：今回は実装を見送る（保留）**。理由：
  1. 最終的にArtifactのDBへ書き込む部分は問題1と全く同じ「無人実行での承認待ち」の壁に当たる。つまりGitHub Actions化しても**ダッシュボード自動更新という本来の目的は達成できない**（問題1が解決されない限り、データを取得できても書き込めない）。
  2. 得られる効果は「正しいKPI値がリポジトリ内のどこかに記録され続ける」ことのみだが、そのためにnote.comのHTMLスクレイピング（ページ構造変化に弱い）・YouTube Data APIキーの取得とGitHub Secretsへの登録（本人の追加作業が必要）・新規ワークフローの保守という**新しい失敗点・保守コストを増やす**ことになり、限定的な効果に対してコストが見合わない。
  3. 問題1（Anthropic側のプラットフォーム不具合）が解消されれば、CCRルーティンのegressアローリスト制約さえ解消されるか、あるいはGitHub Actions側でデータ取得だけ先に済ませておく構成が活きてくる可能性があるため、**問題1の帰趨を見てから再検討する方が合理的**。
- **再検討のトリガー**：(a) Anthropicから問題1（write_db承認プロンプト）の修正・回避策の連絡があった場合、(b) 本人からKPIの推移をダッシュボードと無関係に記録・分析したいという独立したニーズが出てきた場合、のいずれか。
- **当面の運用**：KPI（フォロワー数・記事数・登録者数・長尺動画数）は自動更新が機能していないため、本人が気づいたタイミングで手動更新を依頼する運用を継続する。

   - **運用・グロース視点**：配信方針は5タイプ診断アプリと同じ型（LINE公式アカウントのリッチメニュー／固定リンク経由の「ソフトな限定公開」＝URL非公開・LINE配信のみ、本格認証はなし）を踏襲する方針で変更なし。新しいホテル・航路を追加するたびにデータを追記・再デプロイして「更新しました」とLINEで告知できる継続資産として運用しやすい。note記事側からもこのサイトへ誘導し、逆にサイトの各詳細から関連note記事/動画に飛べるようにして双方向の導線を作る。
   - **結論**：3視点とも構想・プロトタイプに合意。実データ（宿泊リスト・移動履歴）を本人から受領し次第、サンプルデータと差し替えて本実装へ移行する。必要データ項目：
     - ホテル側：ホテル名・ブランド・国/都市・緯度経度・宿泊時期・一言感想・客室タイプ・関連記事/動画URL・**評価（100点満点）**
     - 航路側：出発地/到着地の緯度経度・種別（飛行機/船）・航空会社/便名/機材 or 船名・日付・**評価（100点満点）**
   - **評価（100点満点）の仕様（確定）**：本人提供の`ラグジュアリーホテル評価フレームワーク.xlsx`（既存note格付け記事で使用中の採点方式）に準拠。ホテル側は「接客・サービス品質25%／施設クオリティ20%／ロケーション・眺望20%／内装・インテリア15%／地域性・独自性15%／コスパ5%」の6軸それぞれを5点満点で入力してもらい、サイト側で自動的に加重計算して100点満点の総合スコアを算出する方式で実装済み（本人が100点満点の値を手計算して渡す必要はない）。xlsxの実データ（例：リッツカールトン日光 5/5/5/5/5/4→99点）で計算式が一致することを確認済み。ドロワーに総合スコアとレーダーチャート（6軸内訳）を表示し、ブランドギャラリーのカードにもスコアバッジを追加。航路（飛行機/船）側は専用フレームワークがないため、軸分解のないシンプルな100点満点の単一スコアのままとする方針で確定。
